4 / 10 · 上游教育场景

Agent 重复退款：超时不是执行失败。

发生了什么

同一笔退款在下游已执行，但网关未及时返回。另一个实例再次发起调用，生成了不同的调用 ID，造成重复退款。

最容易误判什么

每次重试生成一个新随机 ID，或只在 Agent 内存里记录“已执行”，都无法约束下游业务副作用。

对我们的用途 · 研究建议

适用于我们以后让助手发消息、提交工单、改权限或删除数据。

处理顺序

  1. 为同一次业务动作保存稳定操作 ID，并把建议、批准、提交和结果分别记录。
  2. 下游按该 ID 原子去重；超时标记为“结果未知”，先查询或对账，再决定后续动作。
  3. 若下游不支持去重或查询，先限制到建议或人工处理；逐步验证后再开放自动执行。

如何证明有效

模拟并发、超时和响应丢失，同一业务动作仍只有一次结果；未知状态可以被查询和收敛。

要留下的产物

工具执行契约：操作 ID、授权、状态查询、去重、审计和人工处理入口。

概念解释 · 幂等 = 重复提交同一个业务操作不会重复产生副作用。ID 应识别业务动作；合法的第二次操作必须有新身份。
自测：接口超时后，直接指数退避重试是否足够？（展开参考判断）

不够。先判断结果是否可查询，并复用同一个业务操作 ID；无法确认结果时进入对账或人工处理。

Technical guide / 先理解，再选型

六组技术概念，连接到具体动作。

读完应能回答：什么时候用、先做什么、如何检查。写工具幂等、知识生命周期与任务恢复的细节见上方案例。

RAG：先找到第一处出错的位置

检索增强生成：先查资料，再让模型依据资料回答。

源数据 → 解析与版本 → 切块和索引 → 权限过滤 → 召回与排序 → 上下文 → 生成与引用

什么时候用
需要从可更新、可引用的资料中回答问题。
第一步怎么做
保留失败问题，检查正确文档是否入库、用户是否有权、正确段落是否召回、是否进入上下文、引用是否支持结论。
怎样检查
分别评估覆盖、新鲜度、检索命中、引用支持和任务完成情况。
常见误区

源文档缺失或版本错误，通常无法靠换一个更强模型补救。

工作流与 Agent：按路径是否确定来选

工作流由代码决定步骤；Agent 根据中间观察选择下一步，两者可以组合。

固定控制流程 → 局部模型判断 → 参数校验 → 有限工具执行 → 检查完成条件

什么时候用
步骤明确时优先固定流程；路径依赖中间信息且结果可验证时，再考虑让模型决策。
第一步怎么做
先写目标、完成条件、允许工具、最大步骤、时间费用上限、停止条件和人工入口。
怎样检查
任务不会无限循环；遇到权限不足、预算耗尽或结果不可确认时有明确状态。
常见误区

增加多个 Agent 并不自动提升质量；只有上下文、权限、工具或任务边界不同才值得拆分。

上下文与 Skill：让方法按需进入任务

上下文包含指令、资料、工具、历史和状态；Skill 用来组织可复用步骤、参考和检查。

任务识别 → 加载相关方法 → 获取当前证据 → 执行 → 检查产物

什么时候用
同一工作方法反复使用，且可以描述触发条件、所需输入与完成标准。
第一步怎么做
只加载当前需要的资料；保留目标、决定、待办和来源；给记忆记录时间与作用范围。
怎样检查
旧目标不会覆盖新目标；检索文档中的指令不会升级成系统规则。
常见误区

把所有资料写进一个巨大的提示词，容易带来冲突和噪声；权限仍需系统强制。

MCP 与 A2A：连接以后，责任仍要定义

MCP 连接工具与资源；A2A 支持独立 Agent 之间交换任务与结果。这里仅概括用途，不追述具体规范版本。

身份确认 → 能力与输入契约 → 有限授权 → 任务或工具调用 → 状态与产物验证

什么时候用
工具需要标准接入，或独立系统间确实需要任务协作时。
第一步怎么做
明确谁授权、允许什么、超时归谁处理、任务在哪里保存，以及对方输出如何校验。
怎样检查
重复请求、撤权、对端失败和重连不会扩大权限或丢失责任。
常见误区

协议解决连接形式，业务幂等、结果正确性和恢复机制仍由应用负责。

评测与观测：让改动可比较、失败可解释

评测检查预期结果；观测记录运行时发生了什么。二者通过请求与版本关联。

固定样本 + 固定版本 → 运行 → 分组比较 → 定位偏离 → 修复 → 回归

什么时候用
每次改动提示、模型、检索、工具、知识或策略之前和之后。
第一步怎么做
从正常、边界和事故中建立样本；关联请求 ID、版本、检索文档、步骤、耗时和结果。
怎样检查
能复现旧基线；高风险错误独立判断；日志只保留排障必要的信息。
常见误区

总体平均分会掩盖少量严重错误；保存全部原文也可能引入新的信息暴露。

成本与延迟：先分解，再优化

总耗时包括排队、检索、生成、工具和后处理；成本还包括重试与人工复核。

记录各段耗时 → 找主因 → 减少多余调用 → 缩短上下文 → 按需缓存或并行 → 重测

什么时候用
用户等待过长，或规模扩大后单任务成本不可接受。
第一步怎么做
先移除无用调用，再考虑并行独立步骤或缓存；缓存需要身份隔离、失效条件与命中监控。
怎样检查
比较同类任务的耗时、费用和质量，确认优化没有增加重试、错误或人工负担。
常见误区

只看模型单次价格，会漏掉长上下文、多次重试和工具执行的总成本。

Put it to work / 我们怎么开始

把“做一个知识助手”拆成六个决定。

下面是我们的示例练习，不是上游项目的实测结果。先填出答案和证据，再考虑增加功能。

01 · 先定义一个真实任务

例如：客服查找有效退款政策。记录当前查找耗时、常见失败和谁负责验收。

产物：一页目标与范围，不用“完成系统”代替业务结果。
02 · 列出数据与访问边界

先选一个知识范围，登记来源、版本、负责人和用户权限，明确撤回与删除生效时间。

产物：数据与权限表；对应“知识同步”案例。
03 · 跑通一条最小完整链路

输入问题 → 查授权资料 → 给出引用建议 → 人工确认。若没有动态决策需求，先用固定工作流。

产物：端到端样例和可追踪记录；对应 RAG 与工作流技术卡。
04 · 先写六类检查样本

有答案、无答案、政策过期、跨权限、重复操作、断线恢复。每类注明预期结果；未启用写工具时，检查其不可调用。

产物：小型评测集；样本量与阈值按实际风险另定。
05 · 明确扩大与停止条件

先让一小组真实用户试用。引用正确、任务有改善后再扩大；出现越权或错误动作时停止并回退。

产物：试点范围、结果记录和恢复责任人。
06 · 用第二个场景检验复用

换一个知识域，观察哪些检索、权限、评测规则仍成立。将共同部分提为模板，保留领域差异。

产物：可复用部分与定制边界；对应“连接器产品化”案例。

Our take

收藏一套准备资料，
