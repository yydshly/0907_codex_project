# 效果扩展与产品化路线

2026-09-08。基于已保存的 tail-v4 和当前 timing-v5。本文是下一阶段方案，不代表已实现实时聊天、在线嘴型或完整角色 SDK。

## 产品方向

结合此前桌面陪伴、台湾口音、半身女性角色与情绪回应的目标，第一款产品建议定位为「能持续对话、对事件做出合适反应的桌面陪伴角色」。先用一个角色完成一个完整使用场景，再扩展多角色、定制肖像或面向其他业务的角色服务。

用户价值需要通过持续使用验证：回应是否贴合上下文、是否及时、是否记得用户允许保存的信息、动作是否增加陪伴感。视频数量、分辨率或动作幅度不能单独代表价值。

## 效果扩展：从三个片段到可控表演

建议第一批覆盖六种行为：

| 行为 | 表情/动作 | 触发方式 |
| --- | --- | --- |
| 倾听 | 稳定注视、自然眨眼、偶尔小幅点头 | 用户讲话时，避免不停点头 |
| 思考 | 短暂偏头或移开视线，然后重新注视 | 等待回应生成时，不用反复口头填充掩盖延迟 |
| 温柔安慰 | 眉眼放松、轻微前倾、语速稍慢 | 用户表达疲惫或需要鼓励 |
| 调皮 | 轻挑眉、短笑、轻微侧头 | 对话允许的玩笑、轻松提醒 |
| 轻微不满 | 轻皱眉、小幅摇头、短暂抿嘴 | 明确的角色表演意图；不能沿用微笑素材冒充生气 |
| 肯定/庆祝 | 微笑、点头、小幅手势 | 用户完成任务或业务事件触发 |

先做约 12～18 个经过筛选的小幅动作素材，作为第一轮素材目标而非已完成数量。每个素材记录：角色版本、动作意图、强度、是否适合说话、嘴部是否遮挡、头部姿态范围、入口/出口姿态、可循环区间。

效果优化分为三层：

1. 面部质量：牙齿、嘴角、身份一致性、侧头与遮挡。固定素材与台词做对照，必要时比较其他驱动模型；不要继续加大模糊。
2. 表演质量：表达同一种意图的台词、声音、眉眼和动作一致。嘴型控制拥有口腔主要控制权，其他表情驱动应限制区域和强度，防止二次覆盖嘴型。
3. 连续性：不只验收单个动作，还要验收倾听→回应、调皮→平静、打断→重新倾听等转场。光滑的交叉淡化可能仍有重影，最终要靠相容姿态和专门过渡素材。

技术候选中，[LivePortrait 官方实现](https://github.com/KlingAIResearch/LivePortrait)提供肖像驱动、编辑、区域控制及眼唇重定向，可用于验证面部与头部控制。它不等同于完整的语义驱动半身手势系统，也不能仅凭支持编辑就断言音频驱动链路已就绪。

[MiniMax WebSocket TTS 文档](https://platform.minimax.io/docs/api-reference/speech-t2a-websocket)可作为流式语音接入的依据；具体模型、音色和情绪参数需按能力表适配。现有代码的 MiniMax 适配器仍是同步 HTTP、`stream=False`，尚未实测用户账户。台湾口音与情绪表现应试听验收，不能只看参数名。

## 表演意图协议

业务/对话层输出受限意图，例如：

```json
{
  "text": "今天辛苦了，先休息一下吧。",
  "intent": "comfort",
  "intensity": 0.35,
  "gesture": "small_nod",
  "gaze": "user",
  "return_to": "attentive_idle"
}
```

这些值由服务端校验并映射到已存在的动作，不直接允许模型任意制造不支持的手势。动作事件绑定实际语音时间轴：如在最后一句结束时点头一次，而不是每个音频块都点头。

例：「今天好累」→角色保持倾听→返回安慰意图与回复→语音按匹配语气播放→眉眼放松并轻点头→尾音后回到温和待机。该链路同时服务效果展示和产品交互。

## 产品架构与最重要的技术验证

推荐验证的运行方式：离线制作角色与动作素材；在线生成对话和语音，复用动作模板与预处理结果，只计算必要的嘴型/表情。先测端到端速度和质量，再确定在线驱动模型与部署。

当前 8020 仍是预生成播放，本地 MuseTalk 历史生成耗时约为几十秒处理一段 4 秒视频。当前后处理几秒完成不能代表新台词的完整生成耗时。浏览器的取消也只取消播放/加载，不会自动取消未来服务端 GPU 任务。

建议分层：

| 层 | 职责 |
| --- | --- |
| 业务与对话 | 用户输入、上下文、允许保存的记忆、任务/提醒等业务事件、表演意图 |
| 角色运行时 | 语音生成、动作选择、嘴型/表情、时间轴、打断和取消、待机恢复 |
| 媒体与模型服务 | GPU 任务、预热、缓存、版本、输出质检、错误回退 |
| 客户端 | 音频主时钟、媒体缓冲、字幕、麦克风、角色界面与状态反馈 |

输入到反馈的链路为：语音/文字 → 对话回应与表演意图 → 语音 → 嘴型与动作调度 → 播放 → 放松/待机。提醒或学习任务完成等业务事件也进入同一个意图入口。

必须先做在线可行性实验：测输入结束到首声音、首画面、稳定播放之间的延迟；测口型处理能否持续跟上音频、长时间是否积累延迟，以及打断后旧任务是否继续占用 GPU。若本地速度不足，再比较远程 GPU、其他视频驱动后端或三维驱动路线。预制动作能减少重复工作，但不能凭此宣称在线生成已实时。

## 第一版产品范围

建议以「一个角色完成连续陪伴对话」为首个产品闭环：

- 一个经过验收的角色和一组可信动作，覆盖倾听、思考、安慰、调皮、轻微不满、肯定。
- 文字与按键语音输入，真实动态回复；字幕、立即停声、打断与重新开口。
- 会话上下文，以及用户可以查看、修改、删除的少量长期偏好。
- 一个具体使用场景，例如每日交流与专注任务完成后的鼓励；主动提醒需要用户设置频率和时间。
- 失败时提供明确的文字/语音回退和可见状态，不让人物一直假装说话。
- 后台记录每轮的延迟、失败原因、模型/素材版本和生成成本。

首版范围不包含任意人物的一键高质量定制、任意复杂动作、未经验证的精准愤怒表演或无限并发。用户输入肖像时，需要新增角色制作与验收流程，不能把替换图片路径当作完整定制能力。

## 业务扩展与复用

在同一角色运行时上，业务差异主要位于内容、知识、记忆与事件：陪伴产品处理日常交流；学习产品处理题目、课程和学习进度；导购/客服处理商品知识和业务流程。面部时间处理、语音适配、打断和播放组件可共用。

先交付一个业务，再抽象面向多业务的 API，避免未验证使用需求就建设角色市场或庞大平台。

## 成本与验收

单轮成本应拆成语言模型用量、语音字符/音频用量、GPU 推理秒数和媒体传输存储。缓存通用动作、模型预处理和常用固定回应；用户专属新台词不能假定总能命中缓存。优先取消已打断的任务，避免为不会播放的结果继续付出成本。

不先承诺固定价格或支持人数，用目标并发下的实际 p50/p95 延迟、失败率、GPU 使用与每有效对话分钟成本决定限额和收费方式。

建议验收分三轮：

1. 表演：同一句话表达多种意图，盲看/盲听能区分，身份一致，连续待机不明显机械重复。
2. 对话：持续多轮，覆盖长句、停顿、网络抖动、打断与快速重新输入；无旧回复抢占和累计音画漂移。
3. 产品：小范围用户反复使用，比较带角色与纯语音/文字版本，确认角色表演确实增加价值，再扩大资源投入。

## 下一步可执行里程碑

第一阶段推进两项工作：制作六类表演样例；建立一条新台词到有声表演的在线性能实验链路。

阶段出口：有可评审的效果矩阵，并用数据确定在线驱动路线。随后实现一个角色的连续对话闭环，再增加记忆与业务事件。继续保留 8021 的认可基线用于回归。
