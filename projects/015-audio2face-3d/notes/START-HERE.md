# 以后重新理解这个项目，从这里开始

记录日期：2026-09-08。本文描述本项目已经接入的版本与实现，不代表上游所有版本的能力，也不代表后续账户配额或服务始终可用。

先打开 [后续分析索引](REVIEW-MAP.md)：包含远端人物选择 / 对话页、能力与代码映射、成本分界、恢复检查以及下轮验证项。

## 1. 先分清“这个库”指什么

**NVIDIA Audio2Face-3D 原库**解决声音到三维面部运动。它不包办照片生成、语言对话、语音合成和身体动作。

**我们的 015 子项目**已经扩展成数字人物实验系统，包含两条独立路线：

- 视频：照片 → LivePortrait 或 Hailuo 动作素材 → MiniMax 回复与语音 → 本地 MuseTalk 口型 → 稳定、合成、播放。
- 3D：音频 → 本地 Audio2Face Mark v2.3 → 面部还原/角色适配 → Three.js 显示 Mark 或 Camila。

这两条路线不是前后依赖。当前“用户换照片，后续流程继续复用”的目标主要走视频路线。3D 路线需要另外准备与适配角色。

## 3. 原库、模型组件、自研代码的边界

| 层 | 组件 | 在这里做什么 |
|---|---|---|
| NVIDIA 上游入口 | vendor/Audio2Face-3D | 组件入口与原始资料 |
| 上游 SDK 与训练资料 | vendor/Audio2Face-3D-SDK、vendor/Audio2Face-3D-training-framework | 参考推理输入输出等约定；本机演示直接用 ONNX Runtime，没有运行训练流程，也没有复刻完整 SDK 后处理 |
| 三维几何来源 | vendor/Maya-ACE、vendor/Camila | Mark 几何与 Camila 角色资产；各自许可不同 |
| 动作模型 | LivePortrait / MiniMax Hailuo / 早期 LTX-Video | 产生动作视频，互为不同版本的动作来源 |
| 口型模型 | MuseTalk，含 Whisper、VAE、U-Net | 声音特征 + 面部特征 → 音频匹配的面部画面 |
| 辅助模型 | facexlib 的 RetinaFace、FAN、ParseNet | 找脸、找关键点、分割语义区域；不能直接产生完整说话效果 |
| 我们的准备层 | 人物登记、检测框/蒙版/VAE 缓存 | 将不同动作来源接到同一口型流程；不是 LivePortrait 的核心动画原理 |
| 我们的优化层 | 时序平滑、光流稳定、句尾回落、动作节奏 | 减少闪动与衔接问题，不代表已经消除全部视觉缺陷 |
| 我们的应用层 | 会话、任务、人物隔离、分段播放器 | 组织所有组件形成可操作演示 |

## 4. 几个最容易忘记的原理

- **口型不是按音量开合嘴巴。** MuseTalk 使用音频特征生成画面；我们另外用音频能量控制句尾融合权重与半身动作节奏。
- **头肩动作不是每句话重新生成。** 人物准备时保存有限动作片段，每次回复选取并复用；新增身体手势需要额外素材或不同动作系统。
- **蒙版不是模型。** 蒙版是一张表示替换区域与融合强度的图；ParseNet 提供语义分割，我们再限制区域、平滑并羽化边缘。
- **VAE 潜变量不是新人物模型。** 它是输入图像的编码。缓存潜变量是在省重复计算，没有按人物重新训练。
- **Whisper 在当前口型流程里不是用户语音识别。** 它用于音频特征提取；当前对话输入仍为文字。
- **3D 里的模型有两种含义。** Audio2Face 是神经网络模型；Mark/Camila 是被驱动的人物几何资产。下载神经网络不等于自动获得任意人物资产。

## 5. 为什么最后拼成这套方案

| 遇到的问题 | 采用的选择 | 获得什么 | 保留的代价或边界 |
|---|---|---|---|
| 用户希望照片变成写实人物 | 从原始 3D 研究扩展视频路线 | 不要求用户先做 3D 建模与绑定 | 像素身份一致性和嘴部细节可能变化 |
| 早期照片口播身体较静止 | 使用 LTX 动作，再增加 Hailuo 半身动作 | 身体、肩膀也能运动 | 云端准备耗时、额度与动作遵循性 |
| 通用本地面部版仍显呆滞 | 保留 LivePortrait，并新增自然半身选项 | 同一上传流程可选不同动作来源 | 自然半身只完成一个人物的完整验证 |
| 已有视频不能说新台词 | MuseTalk 按新音频重绘嘴部 | 动作素材可复用到多句台词 | 需要每次本地推理，嘴角表情可能受影响 |
| 嘴部闪动、说完仍颤抖 | 确定性编码、浮点裁切/平滑、正确蒙版、光流和句尾回落 | 减少处理链路引入的异常 | 仍受源视频自身微动与生成细节影响 |
| 多次调用与恢复可能浪费资源 | 保存云端任务 ID、缓存、失败状态与显式重建入口 | 尽量复用已完成工作 | 未取得任务 ID 的提交不能保证未扣费 |

详细证据：mouth-mask-fix.md、mouth-stability.md、speech-tail-fix.md、natural-body-v2.md。这里描述历史工程选择，不是模型排名。

## 6. 当前状态：什么已经有，什么还没有

- 已有：本地 Audio2Face 推理、Mark / Camila 三维面部演示；照片自助准备、MiniMax 文字对话/TTS、本地 MuseTalk、新回复视频与播放。
- 已有：本地面部版两个不同人物的流程验证；自然半身版若安六种动作及同音频对照。具体素材与任务 ID 见 user-avatars-v1.md、natural-body-v2.md。
- 当时阻断：第二个自然半身人物遇到 MiniMax 2056 时段资源限制。记录的是当时结果，恢复操作前应重新检查，不推断当前额度。
- 尚未完成：任意照片质量保证、长时间不重复的自然动作、语义级手势、无缝情绪切换、实时视频通话、麦克风输入、3D 完整身体动画。
- 自然半身测试：4.52 秒结果本地渲染约 8.172 秒，复用音频；不能当作完整首句响应时间。见 natural-body-v2-verification.json。
- 自动检查证明文件、缓存、音轨与特定静音帧正确，不等于主观自然度已经达标。

## 8. 以后重启与恢复，先做什么

1. 先保留工作区、配置引用和数据目录；代码快照不包含所有视频或权重。
2. 检查模型文件、Python 环境和 FFmpeg 是否存在。视频运行环境目录仍叫 `.cache/sadtalker-venv`，当前核心并不是 SadTalker。
3. 在项目目录使用 `start-performance.ps1` 启动 8022；`start-complete.ps1` 启动 8020；`start.ps1` 启动 8015。这些命令只负责现有环境下启动，不保证补齐缺失模型。
4. 先打开效果总览播放已有片段，确认视频与 3D 资产正常；再用已有 WAV 验证本地口型；最后才调用远端生成。
5. 服务端 `.env.companion` 引用共享 MiniMax 配置。密钥不存入说明文档、网页或快照；新机器要重新配置实际路径。
6. 缺少环境时，按 README 的原始安装记录、requirements、模型下载脚本及版本清单恢复。空白机器完整安装尚未做新的端到端验收。

### 值得保留的数据

- `vendor/`：上游代码、模型权重、人物资产；体积较大，并受各自许可约束。
- `.cache/avatars/`：人物照片、动作视频、准备状态和口型缓存。
- `.cache/performance-jobs/`：回复音频、生成视频、任务与审计数据。
- `.cache/complete/`、`.cache/motion/`：此前 8020 接受版本与原动作素材。
- `.cache/camila/`、`demo/assets/`：三维演示所需角色与样例数据。
- `.cache/releases/`：阶段代码快照与部分基线；不能当作包含全部依赖的安装包。
- `notes/`、`config/`：原理、决策、测试、版本与下载清单。

原始图像、视频、3D 角色、权重和代码的授权应分别看；不能由某一个库的许可证推导所有产物可发布。

## 9. 出问题时，按现象定位

| 现象 | 优先检查 |
|---|---|
| 嘴部抖动或黑块 | 原动作是否已抖动；检测框是否跳；ParseNet 标签是否匹配；蒙版、VAE 编码与时序稳定 |
| 句尾嘴巴不停 | 音频尾部是否有声音；envelope / timeline；原动作视频本身是否开口 |
| 动作呆滞、重复或突然跳变 | 选中的是面部版还是半身版；动作源质量、片段时长、状态与循环衔接 |
| 嘴型不跟音频 | 音频格式、帧率、Whisper 分块、动作采样与缓存索引是否一致 |
| 新人物变成旧人物 | avatar_id、资源路径、源文件散列、缓存失效与会话人物绑定 |
| 云端任务失败 | generation.json、任务 ID、供应商错误码和原始记录；未知提交结果不要盲目重发 |
| 3D 嘴型奇怪 | 先比较官方 Mark 输出，再检查 Camila 适配与绑定，不先认定是口型模型失效 |
| 回复少、语气不合适 | 对话提示词、回复长度限制、音色与 TTS 情绪参数；不是嘴型模型决定 |

## 10. 下次继续推进的优先级

1. 完成不同照片的受控质量验证，明确输入边界；不以增加演示人物数量代替验证。
2. 降低人物准备成本：先验证少量动作、按需补充、显示任务数量和实际用量。当前上传实现仍默认六种，优化未落实。
3. 改善循环与情绪切换，在已有音频与视频上对照，避免 TTS 差异干扰判断。
4. 完成冷启动部署包与恢复演练，记录完整耗时与失败恢复。
5. 最后再扩展实时输入、更多手势或产品业务。
