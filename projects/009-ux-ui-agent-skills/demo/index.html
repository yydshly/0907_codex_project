03 / HOW IT WORKS

把模糊要求，拆成可检查的步骤。

核心机制是按需读取上下文、用 Token 统一表达、通过工具反馈修正。实际设计与代码生成由宿主 AI 完成。

  1. 01理解需求

    判断要设计、改版
    还是审查

  2. 02按需读规则

    组合组件、主题
    风格与框架知识

  3. 03生成界面

    输出主题、代码
    及适用交互状态

  4. 04检查与修正

    静态与浏览器检查
    发现问题后重做

  5. 05人工判断

    视觉是否合适
    业务是否可用

05 / OUR OPPORTUNITY

最值得沉淀的，是我们自己的经验。

采用建议

先采用 统一 Token、组件状态规范、实际页面验证，
再加入品牌、业务和中文体验规则。

先做 · 建立基础

让新页面沿用已有标准

加入自有主题、现有组件与正反例；把检查目标接到真实页面。

  • 品牌与明暗主题
  • 适用交互状态
  • 筛选、排序与确认流程
再做 · 加入场景

让界面符合真实业务

补充领域交互和中文规范，避免只完成视觉表面。

  • 权限、审批与失败恢复
  • 中文字体、长内容和金额
  • 设计工具与组件映射
持续 · 记录证据

让有效经验进入模板

将评审发现转成触发场景、正确行为、反例和检查方法。

  • 固定任务对照实验
  • 缺陷、返工与耗时记录
  • 跨任务验证后再推广
如何判断它对我们真的有帮助？＋

选一个含筛选、表格、弹窗、加载、错误和空状态的真实页面。固定需求、模型、框架和完成标准，在独立会话中比较当前方式与加入核心规则后的方式。

记录：首次交付完整性、交互缺陷、视觉一致性、人工修改轮数、总耗时和可取得的模型用量。一个任务只验证可行性，多种任务重复后再判断总体收益。

这是后续建议，尚未执行。与现有 Effective HTML 研究中的场景化生成规则可互补，组合收益仍需实测。

06 / EVIDENCE & LIMITS

知道能做什么，也知道证明了多少。

01 / 检查目标

示例通过 ≠ 产品通过

默认总检查大量指向上游 examples。要检查我们的界面，必须绑定实际页面和关键状态。

02 / 运行条件

区分通过与未执行

完整检查需要 Python、Node、Playwright 和浏览器。部分无浏览器或无目标分支会跳过，不能直接把零退出码视为合格。

03 / 质量边界

检查无法替代审美与业务判断

禁止 Emoji、限制等宽卡片等规则带有作者偏好。交互状态变化也不等于业务逻辑正确。

04 / 效果证据

有初步记录，仍需我们的验证

作者记录两次盲测子代理取得 14/14。本研究未复跑，不能据此推导普遍效率或审美提升。
