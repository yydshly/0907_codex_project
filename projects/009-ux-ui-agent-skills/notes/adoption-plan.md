# 扩展方向与验证计划

以下均为建议，尚未实现或执行。目标是验证能否降低我们的返工并提高界面一致性，再决定采用范围。

## 扩展方向

| 优先级 | 方向 | 具体内容 | 验收关注点 |
| --- | --- | --- | --- |
| 高 | 自有主题与组件 | 品牌 Token、现有组件映射、页面正反例 | 新页面沿用已有规则，主题切换完整 |
| 高 | 实际产物检查 | 对实际页面执行静态、渲染与交互检查；未运行即失败 | 不能只检查上游示例 |
| 高 | 业务流程 | 权限不足、审批、撤销、批量操作、失败重试 | 关键路径真实可用 |
| 中 | 中文与本地化 | 中文字体行高、长名称、日期金额、错误文案 | 长内容及小屏无损坏，表达符合业务 |
| 中 | 按任务加载 | 将可复用规则接入目标宿主的项目入口和技能发现方式 | 能加载正确知识，避免全量规则干扰 |
| 中 | 设计工具同步 | Token 与 Figma Variables、代码组件建立对应关系 | 明确唯一数据源，差异可追踪 |
| 后续 | 团队评测集 | 保存典型任务、缺陷和评审结论 | 能重复比较收益与成本 |

## 最小对照试验

**任务：** 同一份真实需求，制作包含筛选、数据表格、确认弹窗、加载、错误和空状态的管理页面，并支持窄屏及明暗主题。

**比较方式：** 一组使用当前工作方式，另一组加入选定的 Token、组件状态和检查规则。固定需求、模型、框架、素材、完成标准和时间记录方式；使用独立会话，避免第二组直接看到第一组的修正经验。

| 指标 | 记录方式 |
| --- | --- |
| 首次交付完整性 | 按预先写好的业务清单逐项检查 |
| 交互缺陷 | 记录筛选、排序、弹窗确认与取消等真实操作结果 |
| 视觉一致性 | 按统一主题和组件约定检查 |
| 响应式与无障碍 | 对实际页面检查，记录通过、失败、跳过 |
| 人工返工 | 记录修改项、轮数及用时 |
| 总成本 | 记录总耗时及可取得的模型用量 |
| 主观质量 | 隐去生成方式后评审，保留具体理由，避免伪精确总分 |

先做一个任务验证接入是否可行；在不同页面上重复后再判断总体收益。单次结果仅证明该样例的表现。

## 采用决策

- 能减少重复缺陷且成本合理：将验证过的规则加入我们的项目模板。
- 只有主题一致性收益：仅采用 Token 和组件规范。
- 规则导致明显限制或频繁误报：调整具体规则，再评估。
- 主要依赖人工补救：保持参考资料定位，暂不扩大接入。

## 长期沉淀

将评审发现转成“触发场景 → 正确行为 → 反例 → 检查方法”，并记录适用范围。优先积累我们自己的业务和设计经验，再按需要引用外部风格。
