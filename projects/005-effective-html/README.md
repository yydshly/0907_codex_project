# 005 · Effective HTML：面向场景的 HTML 生成技能

> 把特定场景下的内容组织、布局设计、交互实现与验收方法整理成技能，指导 AI 生成可查看、可操作的 HTML 成果。我们主要借鉴其能力组织方式，并按需提取可复用规则。

## 核心理解

Effective HTML 的核心交付格式是 HTML。它将“在什么场景下、按照什么方法、做到什么程度、如何检查”写成 AI 可读取的技能规则。规则涵盖内容忠实、布局层级、视觉方向、交互状态和浏览器验证。

这些规则不是固定页面模板：布局和风格需要服从主题、受众与项目已有规范。技能提供方法，模型理解材料并生成 HTML、CSS、JavaScript，浏览器负责展示和运行。需要图形时，可以在 HTML 中使用 SVG、Canvas 等表达。

因此，可以把它理解为一套**面向具体任务的 HTML 设计与制作指南**。它不独立进行模型推理，也不凭自身增加新的绘图引擎；规则写有验证要求，也不代表每次生成都已实际完成验证。

## 能力怎样组织

六个入口并非六种互斥的页面类型：`html` 是综合入口与分流规则，`design-artifact` 是可与其他技能组合的设计方法，另外四个处理专项问题。

| 技能 | 适合解决的问题 | 主要约束 | 本研究的场景成果 |
| --- | --- | --- | --- |
| `html` | 报告、解释、比较、小工具等综合需求 | 先确定读者任务，再组合内容与交互 | 研究决策简报：证据矩阵与来源下钻 |
| `design-artifact` | 如何形成适合主题与受众的视觉方向 | 配色、字体、布局与动效有明确依据 | 海岸观察专题：主视觉与阅读节奏 |
| `html-wireframe` | 信息怎么分组，任务顺序和导航怎么安排 | 低保真、真实标签、比较实质结构差异 | 客服工作台：三种结构取舍 |
| `html-prototype` | 用户能否完成一个关键流程 | 状态、校验、反馈、恢复路径与交互边界 | 内容审核台：门槛、退回、失败重试 |
| `html-plan` | 如何把原始计划整理得可核对、可执行 | 保留承诺，明确依赖，区分事实和未知 | 知识库迁移：来源、前置条件与回退 |
| `html-diagram` | 如何解释架构、过程、时序、状态等关系 | 先选图形语义，再选渲染方式，保持关系可读 | 异步图片处理：组件连接与异常路径 |

能力依据：[固定版本技能目录](https://github.com/plannotator/effective-html/tree/d95debbaef15af1d201fc6c10c77cf92b524a0d6/skills)。场景演示为本研究参照技能制作的原创成果，并非上游预置应用；原型使用示例数据，不连接真实业务系统。

## 对我们的意义与参考价值

最值得参考的是**把反复出现的生成任务，整理成可复用的约束和工作流程**。后续研究项目时，可以用同一套方法组织资料、表达关系并核对结果，减少每次重新描述要求的成本。

沉淀一项能力时，建议保留四部分：

1. **场景与目标**：什么情况下调用，读者需要理解或决定什么。
2. **输入要求**：需要哪些材料、权威来源、已有约束和未知事项。
3. **生成规则**：如何选择表达方式、保持语义、处理复杂关系与交互。
4. **验收标准**：结果怎样才算正确、完整、可读和可用。

| 可沉淀能力 | 值得复用或补充的约束 | 适合的验收问题 |
| --- | --- | --- |
| 架构图 | 组件职责、系统边界、连接方向、真实实现与推测分开 | 是否遗漏关键组件？箭头传递的是什么？边界是否有依据？ |
| 流程图 | 起止、判断条件、正常与异常分支、回路 | 每个分支能否走通？失败后如何结束或恢复？ |
| UML 图 | 按问题选择类图、时序图或状态图，遵守对应符号语义 | 参与者、消息顺序、关系和状态转换是否符合所选图种？ |
| 研究报告与计划 | 来源对应、结论边界、依赖与未决事项 | 是否把假设写成事实？原始承诺是否丢失或被扩张？ |
| 交互原型 | 核心任务、关键状态、错误恢复、键盘与窄屏 | 用户能否完成任务？失败与真实系统接管点是否明确？ |

其中，**严格 UML 的语法、领域建模规则和自动校验需要另行补充**。上游提供通用图解指导，不能直接等同于完整 UML 工具。

HTML 适合把说明、图形与交互放在一起。若主要目标是图的维护、语法检查或版本比较，也可以选择 Mermaid、PlantUML、SVG 等格式。我们应复用生成方法与验收要求，再按交付场景决定输出格式。

## 与直接使用大模型的关系

大模型本来可以生成网页和图解。这个库的增量主要是将方法与约束打包，供助手在合适的任务中读取和执行。完整提示词、项目规范也可能覆盖同样要求；已有成熟规则时，应先去重再采用。

规则可能帮助减少漏项，但会增加读取、制作和检查的投入。本研究没有独立的无技能基线，因此不宣称质量或效率提升幅度。判断是否采用，应在同类真实任务中比较内容正确性、任务完成情况、返工和耗时。

**当前建议：作为方法参考库，按需提取，实测后沉淀。** 优先参考图解的关系表达、计划的来源保留与原型的状态覆盖，不需要为了采用它而统一所有成果的外观。
