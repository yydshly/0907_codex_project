## 数据平台迁移：怎样证明可以切换？

- 背景：历史数据要迁到新平台，同时旧系统还在接收更新和删除。管理层希望按日期一次切完。
- 常见误区：行数一样、总金额相同，并不能排除一条重复与一条遗漏相互抵消。双写也不会自动解决冲突。

### 处理顺序

1. 先明确权威写入系统和业务键，区分来源、地区及事件版本。
2. 记录快照水位；历史回填和增量同步分别记录进度，再按业务键与版本合并。
3. 按记录、更新、删除和业务规则对账；先切一个只读业务，再决定写入切换。

- 技术解释：CDC = 持续捕获源端变化；checkpoint = 已确认处理位置。恢复时从可信位置重放，并保证重放不改变正确结果。
- 验收证据：抽查更正和删除能传播；重复回放不产生重复记录；回退后新增数据不丢失。
- 留下的产物：数据契约、分层对账报告、切换与回退清单。
- 对我们的用途（研究建议）：适合我们后续整合多个数据源、替换数据库或重建索引时使用。

**自测：** 两边都是 10 万行，可以切库了吗？

**参考判断：** 还不能。需要确认身份、内容、更新顺序、删除状态和具体业务不变量都一致，并演练回退。

## 隔离部署：离线运行以后怎样维护？

- 背景：客户环境不联网，但模型、依赖、知识和安全补丁仍需要定期导入，系统也需要排障与升级。
- 常见误区：下载模型并校验哈希，只能覆盖一部分交付问题。哈希一致不代表来源可信，也不证明答案和权限正确。

### 处理顺序

1. 登记模型、软件和知识的来源、版本、组件清单及导入责任人。
2. 在模型接触内容前按身份和文档权限过滤；先做限定知识范围的只读试点。
3. 建立离线构建、转运复验、回归、激活与回滚流程，并演练更新和恢复。

- 技术解释：ACL = 资源访问规则；SBOM = 软件组件清单。权限过滤属于检索和系统控制，不能只交给提示词。
- 验收证据：受限内容不进入无权用户的上下文；撤回文档不被引用；旧版本可恢复；升级包可以追溯和重建。
- 留下的产物：离线发布清单、权限评测样本、升级与恢复手册。
- 对我们的用途（研究建议）：遇到私有化或断网环境需求时，用它提前识别长期运维成本。

**自测：** 只读问答没有写工具，还需要权限检查吗？

**参考判断：** 需要。模型可能通过答案、引用标题或日志泄露受限信息。检索前就应限制可见内容。

## 生产事故：模型没变，系统为什么坏了？

- 背景：回答质量下降，同时出现重复业务动作；监控却仍显示较高的“工作流成功率”。
- 常见误区：只排查模型，或者把请求处理完成当作用户任务成功，会漏掉索引、工具重试和指标口径问题。

### 处理顺序

1. 先隔离持续造成损失的写操作，保留受影响记录，建立可用的人工或旧版本路径。
2. 固定健康与失败请求，沿知识、索引、工具和指标逐层比较，并保存版本时间线。
3. 分别修复故障链，回放事故样本，核对受影响业务记录后再恢复能力。

- 技术解释：Trace = 一次任务跨步骤的关联记录。模型、提示、知识、索引、工具和指标都可能独立变更。
- 验收证据：索引覆盖恢复、引用证据正确、业务动作唯一；人工路径和积压恢复均可验证。
- 留下的产物：事故时间线、影响清单、分层假设表和恢复证据。
- 对我们的用途（研究建议）：用于我们后续上线服务的事故排查；减少“随便改一个参数，似乎好了”的判断。

**自测：** 工作流成功率回升，可以宣布事故结束吗？

**参考判断：** 不够。需要核验答案质量、外部业务结果和受影响记录；运行成功与业务成功要分别判断。

## Agent 重复退款：超时不是执行失败。

- 背景：同一笔退款在下游已执行，但网关未及时返回。另一个实例再次发起调用，生成了不同的调用 ID，造成重复退款。
- 常见误区：每次重试生成一个新随机 ID，或只在 Agent 内存里记录“已执行”，都无法约束下游业务副作用。

### 处理顺序

1. 为同一次业务动作保存稳定操作 ID，并把建议、批准、提交和结果分别记录。
2. 下游按该 ID 原子去重；超时标记为“结果未知”，先查询或对账，再决定后续动作。
3. 若下游不支持去重或查询，先限制到建议或人工处理；逐步验证后再开放自动执行。

- 技术解释：幂等 = 重复提交同一个业务操作不会重复产生副作用。ID 应识别业务动作；合法的第二次操作必须有新身份。
- 验收证据：模拟并发、超时和响应丢失，同一业务动作仍只有一次结果；未知状态可以被查询和收敛。
- 留下的产物：工具执行契约：操作 ID、授权、状态查询、去重、审计和人工处理入口。
- 对我们的用途（研究建议）：适用于我们以后让助手发消息、提交工单、改权限或删除数据。

**自测：** 接口超时后，直接指数退避重试是否足够？

**参考判断：** 不够。先判断结果是否可查询，并复用同一个业务操作 ID；无法确认结果时进入对账或人工处理。

## 知识库更新：内容没变，权限也可能变。

- 背景：知识助手持续同步文档。源文件改名、撤销访问权，或某次扫描没有返回全部文件，目标索引可能继续暴露旧内容。
- 常见误区：用内容哈希当文档身份，或把一次扫描缺失直接当作删除，会造成版本关系混乱与误删除。

### 处理顺序

1. 用租户、来源和源端文档 ID 建立稳定身份；内容版本、权限版本与同步批次分别保存。
2. 权限撤回先阻断在线读取，再更新索引和缓存；内容不变时不必重新生成向量。
3. 仅在可信删除事件或完整快照对账后推进删除；检查所有下游副本与缓存是否收敛。

- 技术解释：upsert = 存在则更新，否则插入；tombstone = 删除标记。软删除要求查询立刻排除，物理清理可以随后进行。
- 验收证据：断掉一次扫描不误删；撤权后旧缓存和旧引用不可用；更新、删除、物理清理各有明确时限。
- 留下的产物：文档生命周期表、同步批次对账、撤权与删除测试样本。
- 对我们的用途（研究建议）：我们将资料库接入检索或知识助手时，可据此设计更新与撤销机制。

**自测：** 源端这一轮没返回某文档，能立即删掉目标副本吗？

**参考判断：** 不能只凭缺失判断。先排除分页失败或扫描中断，再使用可信删除事件或完整快照作证据。

## 长任务恢复：页面断开，任务仍有自己的状态。

- 背景：Agent 执行时间较长；用户刷新页面，或者处理任务的服务实例重启，界面丢失输出，恢复时还可能重复调用工具。
- 常见误区：粘性会话只能尽量连回旧实例；文本缓存也无法回答“工具是否已经执行”。

### 处理顺序

1. 创建持久任务并返回 job_id，存储输入版本、步骤状态和结果引用。
2. Worker 领取带版本令牌的租约；旧 Worker 恢复后不能覆盖新执行者的状态。
3. 输出事件按任务编号；客户端凭最后事件编号补读，写工具恢复先查询业务结果。

- 技术解释：fencing token = 区分新旧执行权的令牌；SSE = 服务端向页面推送事件的通道。SSE 本身不保存任务。
- 验收证据：刷新页面、杀掉 Worker、重复领取任务后可恢复；关键步骤不丢、写操作不重复、过期执行者不能提交。
- 留下的产物：任务状态机、步骤检查点、事件记录和恢复演练。
- 对我们的用途（研究建议）：我们以后开发长时间研究、批量处理或内容生成任务时，可复用这个执行与展示分离的思路。

**自测：** 用户关闭网页，是否代表取消任务？

**参考判断：** 不代表。取消应是经过授权的明确状态变化；页面关闭通常只结束观察连接。

## 评测下降：先检查测量，再定位变化。

- 背景：发布后准确率大幅下降，同时某些高风险请求被错误路由；数据、提示或标签格式可能在同一时期变化。
- 常见误区：把所有问题归因于模型，或看到平均分恢复就忽略高风险子集，都会使结论失真。

### 处理顺序

1. 先把高风险请求切到稳定路径，保存失败样本与各组件版本。
2. 检查分母、标签格式、去重和评测代码；用固定请求集重现旧基线。
3. 每次只替换一个变量，定位首个偏离步骤；按风险分组复评并逐步恢复。

- 技术解释：黄金集 = 有预期结果的固定样本集；切片评测 = 按语言、角色、风险或任务类型分组评估。
- 验收证据：原始输出、最终动作和指标计算能对应；高风险分组独立达标；事故样本进入回归集。
- 留下的产物：版本矩阵、固定回放集、分组评测报告与发布门槛。
- 对我们的用途（研究建议）：我们比较提示词、检索策略或模型改动时，用它避免凭几个漂亮样例做决定。

**自测：** 新版本平均分更高，但越权样本失败，能发布吗？

**参考判断：** 不能用平均收益抵消关键权限失败。应为这些错误设置独立阻断条件。

## 跨区域部署：跟着数据流确认边界。

- 背景：多个区域希望共享 AI 能力，但原文、索引、密钥、日志、备份和供应商处理路径受到不同约束。
- 常见误区：设置一个 region 参数，不会自动约束日志、支持人员访问、备份和外部模型调用。

### 处理顺序

1. 列出数据类别、处理目的、流转路径、保留期限和负责确认的业务或专业人员。
2. 将原文、索引与敏感日志保留在批准区域，先用低风险数据范围开展试点。
3. 共用接口和评测格式，按允许范围汇总指标；定义供应商退出、删除和密钥轮换流程。

- 技术解释：数据面处理实际数据；控制面管理配置和策略。共享产品代码不意味着要集中存储客户数据。
- 验收证据：每一条出区数据路径有依据和责任人；日志、缓存、备份及删除流程均覆盖。
- 留下的产物：数据流图、控制矩阵、未决问题与批准记录。
- 对我们的用途（研究建议）：客户有多区域要求时，作为需求发现和工程拆解清单；具体规则须由对应专业人员确认。

**自测：** 去掉姓名后，就能把所有日志集中起来吗？

**参考判断：** 不能这样推断。其他字段仍可能识别个人或包含业务敏感内容，需要结合用途和批准范围判断。

## 没人使用：把质量指标放回真实流程。

- 背景：离线答案表现不错，但用户生成后不采用。案例中还存在等待较长和两个系统间复制的负担。
- 常见误区：增加培训或强制打开页面，可能提高访问量，却不改善任务完成效果。

### 处理顺序

1. 观察打开、生成、等待、编辑、采用和最终结果的完整漏斗。
2. 按角色与任务复杂度拆分，再访谈常用、流失和从未使用的人。
3. 先用小范围实验改善等待或流程切换，再比较处理时间、修改量和风险错误。

- 技术解释：采用率关注输出是否进入实际工作；它要结合质量、编辑负担和业务结果解释。
- 验收证据：衡量建议是否用于下一步动作、整体耗时是否下降，而非只看登录和点击。
- 留下的产物：使用漏斗、分群假设、对照实验和采纳反馈。
- 对我们的用途（研究建议）：我们做的工具或展示页面如果访问多但无后续行动，可以借此判断是内容、流程还是价值问题。

**自测：** 访问量翻倍，就说明工具更有价值了吗？

**参考判断：** 不能直接说明。检查完成结果、耗时与采用行为，排除强制点击和额外操作造成的虚高。

## 连接器复用：抽象稳定流程，保留来源差异。

- 背景：多个客户连接器代码相似，一次认证升级却让多个集成失败。团队希望统一核心并快速接入新来源。
- 常见误区：所有连接器继承同一个类，或统一成一种错误类型，可能隐藏分页、删除和重试语义的差异。

### 处理顺序

1. 梳理认证、分页、游标、写入、删除、权限、错误和健康状态的生命周期。
2. 公共层定义契约，源适配器解释差异，客户字段映射留在配置边界。
3. 选两个差异明显的来源做契约测试与双跑对账，再渐进迁移其他连接器。

- 技术解释：契约测试检查统一接口承诺的行为；适配层保留每个来源对分页、更新和删除的实际含义。
- 验收证据：重复、乱序、限流、撤权和删除均有预期行为；第二个来源验证了复用收益。
- 留下的产物：连接器能力表、适配契约、回放测试和迁移计划。
- 对我们的用途（研究建议）：我们把多个第三方数据源或工具接入同一系统时，用来判断哪些适合共用、哪些应该独立。

**自测：** 两份代码看起来很像，就适合放进共享核心吗？

**参考判断：** 还需比较业务语义和变化维度，并通过差异明显的第二个来源验证，避免把定制复杂度带入核心。

## 技术速查

### RAG：先找到第一处出错的位置

检索增强生成：先查资料，再让模型依据资料回答。

- 何时使用：需要从可更新、可引用的资料中回答问题。
- 链路：源数据 → 解析与版本 → 切块和索引 → 权限过滤 → 召回与排序 → 上下文 → 生成与引用
- 操作：保留失败问题，检查正确文档是否入库、用户是否有权、正确段落是否召回、是否进入上下文、引用是否支持结论。
- 检查：分别评估覆盖、新鲜度、检索命中、引用支持和任务完成情况。
- 易错点：源文档缺失或版本错误，通常无法靠换一个更强模型补救。

### 工作流与 Agent：按路径是否确定来选

工作流由代码决定步骤；Agent 根据中间观察选择下一步，两者可以组合。

- 何时使用：步骤明确时优先固定流程；路径依赖中间信息且结果可验证时，再考虑让模型决策。
- 链路：固定控制流程 → 局部模型判断 → 参数校验 → 有限工具执行 → 检查完成条件
- 操作：先写目标、完成条件、允许工具、最大步骤、时间费用上限、停止条件和人工入口。
- 检查：任务不会无限循环；遇到权限不足、预算耗尽或结果不可确认时有明确状态。
- 易错点：增加多个 Agent 并不自动提升质量；只有上下文、权限、工具或任务边界不同才值得拆分。

### 上下文与 Skill：让方法按需进入任务

上下文包含指令、资料、工具、历史和状态；Skill 用来组织可复用步骤、参考和检查。

- 何时使用：同一工作方法反复使用，且可以描述触发条件、所需输入与完成标准。
- 链路：任务识别 → 加载相关方法 → 获取当前证据 → 执行 → 检查产物
- 操作：只加载当前需要的资料；保留目标、决定、待办和来源；给记忆记录时间与作用范围。
- 检查：旧目标不会覆盖新目标；检索文档中的指令不会升级成系统规则。
- 易错点：把所有资料写进一个巨大的提示词，容易带来冲突和噪声；权限仍需系统强制。

### MCP 与 A2A：连接以后，责任仍要定义

MCP 连接工具与资源；A2A 支持独立 Agent 之间交换任务与结果。这里仅概括用途，不追述具体规范版本。

- 何时使用：工具需要标准接入，或独立系统间确实需要任务协作时。
- 链路：身份确认 → 能力与输入契约 → 有限授权 → 任务或工具调用 → 状态与产物验证
- 操作：明确谁授权、允许什么、超时归谁处理、任务在哪里保存，以及对方输出如何校验。
- 检查：重复请求、撤权、对端失败和重连不会扩大权限或丢失责任。
- 易错点：协议解决连接形式，业务幂等、结果正确性和恢复机制仍由应用负责。

### 评测与观测：让改动可比较、失败可解释

评测检查预期结果；观测记录运行时发生了什么。二者通过请求与版本关联。

- 何时使用：每次改动提示、模型、检索、工具、知识或策略之前和之后。
- 链路：固定样本 + 固定版本 → 运行 → 分组比较 → 定位偏离 → 修复 → 回归
- 操作：从正常、边界和事故中建立样本；关联请求 ID、版本、检索文档、步骤、耗时和结果。
- 检查：能复现旧基线；高风险错误独立判断；日志只保留排障必要的信息。
- 易错点：总体平均分会掩盖少量严重错误；保存全部原文也可能引入新的信息暴露。

### 成本与延迟：先分解，再优化

总耗时包括排队、检索、生成、工具和后处理；成本还包括重试与人工复核。

- 何时使用：用户等待过长，或规模扩大后单任务成本不可接受。
- 链路：记录各段耗时 → 找主因 → 减少多余调用 → 缩短上下文 → 按需缓存或并行 → 重测
- 操作：先移除无用调用，再考虑并行独立步骤或缓存；缓存需要身份隔离、失效条件与命中监控。
- 检查：比较同类任务的耗时、费用和质量，确认优化没有增加重试、错误或人工负担。
- 易错点：只看模型单次价格，会漏掉长上下文、多次重试和工具执行的总成本。
